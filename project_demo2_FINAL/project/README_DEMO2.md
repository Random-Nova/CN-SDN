# Demo 2 – Fair Client Job Allocation and Live Statistics

## What was added

- **Fair client priority:** jobs are queued separately by client ID. The scheduler takes one job from each active client's queue in round-robin order. A client that submits many jobs cannot continuously take every scheduling turn.
- **Worker allocation:** among alive workers, the server chooses the worker with the fewest jobs currently in progress. The worker's reported load is used as a tie-breaker.
- **Live dashboard:** a browser page shows server status, connected/known clients, queue depth, running and completed jobs, worker heartbeat/load, client-wise statistics, and the complete job-allocation table.
- **Job traceability:** every job records the server job ID, client ID, client job ID, job title, assigned worker, state, timestamps, execution duration, retry count, and result.
- **Client output:** each client also prints a compact result table containing the server job ID, client job ID, worker, job title, status, and result.
- **Failover visibility:** a job returned by a failed worker is queued again and its attempt count is increased.

## How is priority decided?

All clients have equal priority. The queue uses **round-robin across clients**, not first-client-wins and not a permanent preference for one client. For example, if client A has A1, A2, A3 and client B has B1, B2, the scheduling order is A1, B1, A2, B2, A3 (assuming both queues are ready and no other client submits a job).

After the scheduler chooses a client job, the worker manager chooses the least-loaded alive worker. Client priority and worker selection are separate decisions.

## Run locally

Open terminals in `project/member_b` (or use the paths shown below).

1. Start the server and dashboard:

   ```bash
   cd project/member_b
   python run_server.py
   ```

2. Start three workers in three other terminals:

   ```bash
   python worker.py w1
   python worker.py w2
   python worker.py w3
   ```

3. Open the dashboard in a browser:

   ```text
   http://127.0.0.1:8000
   ```

4. Submit jobs from separate terminals:

   ```bash
   cd project/member_a
   python client.py client_A sum 6 127.0.0.1
   python client.py client_B reverse 4 127.0.0.1
   python client.py client_C sleep 3 127.0.0.1
   ```

   Use a different client ID for each client. To run the clients on other computers, replace `127.0.0.1` with the server machine's LAN IP and allow TCP ports **5000**, **6000**, and **8000** through the firewall.

## Ports

| Port | Purpose |
|---|---|
| 5000 | Client-to-server job submission and results |
| 6000 | Worker registration, heartbeat, job assignment, and completion |
| 8000 | Live browser dashboard and JSON status API |

The dashboard refreshes automatically every two seconds. It is a standard-library implementation and does not need Flask or any third-party Python package.

## What the dashboard columns mean

- **Server Job ID:** unique ID generated by the server (for example, `j12`).
- **Client ID / Client Job ID:** identifies who submitted the job and the ID used by that client.
- **Job title:** readable task name (not just the internal task key).
- **Worker assigned:** the worker currently handling the job, or `—` while queued.
- **Status:** `QUEUED`, `RUNNING`, `COMPLETED`, or `FAILED`.
- **Times / duration / attempts / result:** submission, execution and completion details, including retries after a worker failure.

## Test the client fairness rule

From `project/member_a`:


This checks that when A has three queued jobs, B has two, and C has one, the order is `A1, B1, C1, A2, B2, A3` rather than running all of A's jobs first.


## Multi-client worker failover test

Run the failover test from `project/member_b` while the server and at least
three workers are running:

```bash
python3 test_failover.py 12 20 127.0.0.1
```

The test distributes jobs across `client1`, `client2`, and `client3` using
separate client connections. This gives the server's fair client queue jobs
from multiple clients, so the existing client-level round-robin scheduler is
exercised. The test prints: (1) jobs accepted by the server, (2) results
delivered to each client, (3) jobs recovered after worker failure, and (4) a
final pass/fail summary.

To demonstrate failover, stop one worker (Ctrl+C in that worker's terminal)
while the sleep jobs are still running. The manager reports the failed worker
and a table containing each affected server job, original client, client job ID,
and requeue action. The result tables then show failed worker(s), final
reassigned worker, and attempt count. If no worker is stopped while jobs are
in flight, the recovery table correctly reports that no retries were observed.

### Scheduling clarification

Client-level job selection remains round-robin: the scheduler takes one queued
job from each active client's queue in turn. Worker selection is a separate
policy: the default is least-loaded worker selection; round-robin worker
selection is used only when the worker manager is configured with `policy="rr"`.
